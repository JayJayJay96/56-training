# OrderHub 培训活动复习摘要

## 这次活动学到什么

这套练习的重点不是把功能做出来而已，而是练习一套可以重复使用的工作方式：

> 先看现象，再追资料流；先确认根因，再修改；修改后用测试和页面验证。

## 1. 先快速读懂陌生项目

OrderHub 是一个 ASP.NET Core MVC / .NET 8 的订单管理系统，主要分成三层：

- `OrderHub.Web`：Controller、ViewModel、Razor View，负责接收输入、调用 service 和显示结果。
- `OrderHub.Core`：Domain、介面和业务规则，例如折扣、订单状态和库存逻辑。
- `OrderHub.Infrastructure`：EF Core、DbContext、Repository、Migration 和 seed data。

基本资料流是：

```text
Controller → Core Service → Repository → DbContext / Database
       ↑                                  ↓
       └──────────── ViewModel / View ────┘
```

几个要记住的项目惯例：Controller 不放业务逻辑；Service 不直接碰 `DbContext`；View 使用 ViewModel；金额使用 `decimal`；预期中的业务失败用 `ServiceResult`，不要为了正常验证错误抛 exception。

另外，`AGENTS.md`、skills、rules 和 subagents 是给 agent 的项目上下文与安全护栏。它们可以减少每次重新说明项目规则的时间，但不能代替人工检查代码和测试。

## 2. 修 bug 的固定流程

这次三个客诉都走同一套流程：

1. 先在页面重现，并记下具体数字。
2. 从 Controller 往下追 Service、Repository 和资料库。
3. 找到第一个错误的状态变化或计算位置。
4. 做最小修改，不顺手重构无关代码。
5. 补一个能证明问题的回归测试。
6. 回到页面确认，再检查 diff 和完整测试。
7. 一个问题一个 commit。

### 客诉 1：分页错位

现象是新订单在第一页找不到，最后一页是空白。实际看到 202 笔订单、每页 20 笔时，第 11 页没有资料。

根因是页面编号从 1 开始，但 Repository 使用了：

```csharp
Skip(page * pageSize)
```

应该跳过前面已经完整显示的页数：

```csharp
Skip((page - 1) * pageSize)
```

这个问题提醒我：分页测试不能只测 `TotalCount` 和 `TotalPages`，还要检查第一页和最后一页实际回传的订单。

### 客诉 2：Gold 重复折扣

商品原价 NT$1,420，Gold 订单正确结果应该是 NT$1,278，但页面显示 NT$1,150.20；Silver 则正常。

根因是 Gold 折扣被算了两次：建单时先修改了快照价格，计算总额时又再次折扣。

正确做法是保存商品原价快照，把折扣集中到 `CalculateTotal`，只保留一个折扣计算点。

这个问题提醒我：看到 agent 说“流程正常”不能直接接受，必须自己跟着实际数字走一遍。1000 经过一次 Gold 折扣应该是 900，不应该变成 810。

### 客诉 3：取消订单没有恢复库存

建立订单时库存从 `N` 变成 `N-1`，取消后应该回到 `N`，但页面没有加回库存。

根因是取消流程先把订单状态改成 `Cancelled`，之后才检查订单是否为 `Pending` 或 `Confirmed`。状态已经改掉后，条件当然不会成立。

修复顺序是：先确认订单可取消，恢复明细对应的商品库存，再把状态改成 `Cancelled`。

这个问题提醒我：状态转换的先后顺序会影响后续条件判断，不能只看最后的状态值。

## 3. 新增低库存页面时的设计重点

练习 3 新增了：

```text
GET /Products/LowStock?threshold=10
```

页面会列出 active 且库存小于门槛的商品，依库存升序排列，并统计近 30 天销量；Cancelled 订单不计入，库存低于 5 的列使用警示色。

需要特别注意的边界：

- 没有 threshold 时默认 10。
- `threshold <= 0` 要回到页面显示验证错误，不能变成 500。
- 条件是 `< threshold`，不是 `<= threshold`。
- 停售商品不能出现在结果中。
- 日期边界和 Cancelled 状态都要在测试中明确放资料验证。

这次补了三个测试：门槛过滤与排序、排除停售商品、近 30 天销量排除 Cancelled 和窗口外订单。

这里有一个值得继续思考的架构取舍：目前查询条件和销量统计主要放在 Repository，`ProductService` 比较像转接。这样能让 EF 查询集中在 Repository，但和 guideline 强调的“业务逻辑放 Core service”并不是完全一致。以后如果继续改，可以先明确哪些是数据库查询表达式，哪些是应该由 Service 控制的业务规则，避免两层职责混在一起。

## 4. 小型重构的原则

练习 4 把 `OrderService.CreateOrderAsync` 拆成两个私有方法：

- `ValidateOrderRequestAsync`：客户存在、明细不为空、数量有效、商品不能重复。
- `ValidateAndAddOrderLinesAsync`：逐笔检查商品状态和库存，并建立订单明细。

重构前后应该保持：

- 对外方法和回传格式不变。
- 错误消息不变。
- 库存扣除行为不变。
- 折扣和订单金额行为不变。
- 现有测试全部继续通过。

好的重构不是“代码看起来更漂亮”就结束，而是要能说清楚：改善了什么，以及明确没有改变什么。

## 5. 测试与验证经验

测试要验证行为，不只是验证某个方法被调用或某个总数存在：

- 分页要验证实际资料。
- 折扣要把建单、快照和总额串起来测。
- 取消订单要同时测状态和库存。
- 新功能要测正常路径和边界条件。
- 重构后要跑完整测试，不要只跑刚改的测试。

本项目原本的 `obj` 目录有 ACL 写入限制，所以在 repository 目录执行测试会失败在构建缓存写入，而不是测试断言失败。后来复制到可写入的干净副本执行：

```text
34 passed, 0 failed, 0 skipped
```

因此报告测试结果时，要区分：原目录执行失败的环境问题，以及干净副本中实际通过的测试结果，不能混在一起写。

## 6. Agent 使用心得

比较有效的 prompt 通常包含四件事：角色、任务、资料上下文和输出格式。

例如不要只说“帮我看项目”，可以说明：

- 先读哪些文件；
- 先给计划还是直接修改；
- 哪些地方不能动；
- 要怎么验证；
- 最后要回报哪些结果。

Agent 很适合快速找文件、整理流程、提出可能的根因，但最终判断还是要靠：

1. 对照实际代码；
2. 对照实际页面数字；
3. 对照测试结果；
4. 检查 diff 和 commit。
